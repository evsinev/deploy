All configuration is supplied through **environment variables**. The server resolves them at
startup through four independent config interfaces; the agent reads two variables directly.
Defaults are shown in the tables below.

<Aside type="danger" title="Secrets">
`REDMINE_API_ACCESS_KEY`, `GITLAB_API_KEY`, `TELEGRAM_TOKEN`, and `DEPLOY_REVIEW_TOKEN` are secrets — provide them via
the environment, never commit them. The tracked `test.env` file currently contains a
live-looking Redmine URL and key; treat it as compromised — rotate it and keep real credentials
out of version control.
</Aside>

## Server

| Env var | Default | Meaning |
|---|---|---|
| `VERTX_SERVER_PORT` | `8080` | HTTP/WebSocket listen port (bound to `127.0.0.1`). |
| `VERTX_ALIASES_DIR` | `./aliases` | Directory of deploy alias `*.yml` files. |

## Dashboard

| Env var | Default | Meaning |
|---|---|---|
| `DASHBOARD_PATH` | `/deploy/dashboard` | Dashboard base path. |
| `DASHBOARD_REFRESH_MS` | `2000` | SSE push interval (ms). |
| `SERVER_LOG_FILE` | `/var/log/deploy-server-1/current` | Server log file tailed on the dashboard's **Log** screen; set it blank to disable that screen. |

## Deploy review webhook

An outbound `POST` sent at **deploy start** so an external service can analyse the release while it
is being rolled out. Disabled by default; when enabled, `DEPLOY_REVIEW_URL` must be set or the
server fails fast at startup.

| Env var | Default | Meaning |
|---|---|---|
| `DEPLOY_REVIEW_ENABLED` | `false` | Enable the deploy-start webhook. |
| `DEPLOY_REVIEW_URL` | `""` | Endpoint the notification is posted to. |
| `DEPLOY_REVIEW_TOKEN` | `""` | Bearer token sent in `Authorization` (**secret**). |
| `DEPLOY_REVIEW_TIMEOUT_MS` | `20000` | Connect/read timeout (ms). |

The request body carries the identity from the alias
[`diff:` block](/deploy/guides/writing-aliases/#deploy-review-webhook) plus both versions:

```json
{
  "project": "payneteasy/paynet",
  "app": "ams2-paynet-proc",
  "instance": "AMS-2",
  "old_version": "3.36.16-117",
  "new_version": "3.36.16-118",
  "deployed_at": "2026-08-11T15:07:39Z"
}
```

Delivery goes through a durable spool (`QUEUE_DIR/deploy-review`), so it survives a restart and is
retried with backoff; it is **at-least-once**, which is safe because the receiver dedupes by
version. `4xx` answers (bad token, bad version format) are dead-lettered immediately instead of
being retried. The notification is only sent for aliases whose `diff:` block is enabled and carries
`project` and `instance` — the plain `?command=run` path never reads the old version, so it sends
nothing.

## Agent

The agent reads exactly two variables, both **required** — the process throws on startup if
either is missing or blank:

| Env var | Meaning |
|---|---|
| `SERVER_BASE_URL` | WebSocket base URL; `AGENT_ID` is appended, so it should end with `/`. |
| `AGENT_ID` | Agent identity (the last path segment the server keys on). |

<Aside type="tip">
The dashboard's **Config** screen renders the effective value of every one of these variables at
runtime (with secrets masked), so you can confirm what the running server actually picked up.
</Aside>
